# IntuneGet v0.8.1

This Docker image update adds persistent server diagnostics and corrects the database migration order. It includes the fixes from [#1490](https://github.com/ugurkocde/IntuneGet/pull/1490) and [#1482](https://github.com/ugurkocde/IntuneGet/pull/1482). The Windows packager is released separately and is unchanged by this release.

## Server diagnostics

Set `INTUNEGET_LOG_LEVEL` to `debug`, `info`, `warn`, or `error` to control server log verbosity. `info` is the default. Restart the server after changing the setting.

Set `INTUNEGET_LOG_DIR` to keep server logs in a folder. Docker Compose defaults to `/data/logs` in the existing data volume. The server creates the folder when it accepts its first log line, rotates `intuneget.log` at 5 MiB, and retains three backups. Bind mounts must allow the container user, UID and GID 1001, to write there. Restrict access to logs and use a separate directory for each server process. See the [self hosting guide](https://github.com/ugurkocde/IntuneGet/blob/v0.8.1/docs/SELF_HOSTING.md).

Server request errors and errors caught by the root, global, and dashboard page boundaries now record a fixed area or route pattern and an optional numeric digest. Reports are bounded and may be suppressed during repeated failures. They do not capture every browser exception. Related to [issue #483](https://github.com/ugurkocde/IntuneGet/issues/483).

## Database setup

Migration version identifiers are now unique, and dependent database objects are created in the correct order. The setup guide explains the Supabase CLI version ordering and how to reconcile an existing migration history without assuming that an old entry proves every schema change ran. Related to [issue #449](https://github.com/ugurkocde/IntuneGet/issues/449).

For an existing Supabase installation, back up the database and follow the [database setup guide](https://github.com/ugurkocde/IntuneGet/blob/v0.8.1/docs/DATABASE_SETUP.md) before applying pending migrations. Updating the Docker image does not repair an existing database history automatically.

## Verification and known limitations

The release pipeline requires native Linux amd64 and arm64 checks of the exact image digest. Each architecture must pass fresh SQLite volume initialization, persistence after container recreation, and upgrade from a disposable v0.7.1 database. Critical vulnerability scanning and digest signing must pass before the stable `latest`, `0.8`, and `0` aliases move.

Windows Docker Desktop confirmation for the reported case in issue #1272 remains pending. Image checks do not establish Microsoft Graph permissions, tenant upload, or device installation success.
