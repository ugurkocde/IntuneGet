# IntuneGet v0.8.5

This app and Docker image update fixes automatic-update history in self-hosted SQLite installations. The local Windows packager has a separate release process and does not need a version bump for this server fix.

## SQLite automatic-update tracking

When a local packaging job finishes, its automatic-update history now becomes Completed, Failed, or Cancelled as appropriate. Successful deployments contribute to the Updated (7 days) counter. Job status, history, and policy failure tracking are saved in one transaction, and repeated completion reports do not count failures twice.

On startup, existing in-progress history linked to finished jobs is repaired. Only the newest attempt changes policy tracking, so older jobs cannot overwrite a newer in-flight update. Existing failure counts are preserved and the failure threshold remains enforced. See [#1705](https://github.com/ugurkocde/IntuneGet/pull/1705), addressing [#1703](https://github.com/ugurkocde/IntuneGet/issues/1703).

Packager health now counts distinct workers observed through job heartbeats in the last five minutes. Idle workers without recent job heartbeats can still report zero; this is not a separate worker registration service.

## Hosted QA groundwork

The release also contains the preparatory VC++ single-attempt identity guards from [#1701](https://github.com/ugurkocde/IntuneGet/pull/1701) and [#1704](https://github.com/ugurkocde/IntuneGet/pull/1704). These do not activate runtime retries or remove existing security and dependency holds.

## Upgrade and verification

After publication, use `ghcr.io/ugurkocde/intuneget:0.8.5`. Back up the database and retain the existing data volume and server configuration when recreating the container. The startup repair runs when SQLite first opens; no manual database edit is required. See the [self-hosting guide](https://github.com/ugurkocde/IntuneGet/blob/v0.8.5/docs/SELF_HOSTING.md).

The existing release pipeline must pass native amd64 and arm64 SQLite initialization, persistence and upgrade checks, vulnerability scanning, and signing before stable image tags are promoted. Unit and integration tests cover completion, repeated reports, ownership, rollback, startup repair and worker heartbeat expiry. Those checks do not establish a successful deployment in a customer tenant or a device installation.
